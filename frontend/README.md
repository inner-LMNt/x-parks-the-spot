## Folder Structure

### `/api`
Contains axios instance:
```typescript
const axiosInstance = axios.create({
  baseURL:
    process.env.NEXT_PUBLIC_API_BASE_URL ||
    "http://localhost:5000/api/unstable",
});
```
The main part of this file is the creation of an axios instance which can be used to make api calls to the given baseURL.
It is `http://localhost:5000/api/unstable` by default, but can be set in `.env.local`.

### `/app`
#### Overview
This houses all of our pages. The file structure is such that the path of the url on the actual site will be derived
from the folder names. For example the `add` folder will be located at `https://websiteurl.com/add'.

There are other custom named folders, for example `\bookings\[parking-space-id]` is a folder that will allow us to have
custom id'd urls for displaying the booking of a specific spot. To handle this, the component has these two lines of code:

```typescript
const params = useParams();
const parkingSpaceId = params?.['parking-space-id'] as string ?? "invalid";
```
#### Conventions
We have a few conventions throughout the `\app` directory.

Pages: Each page has 3 files. The first should be called `FooBarPage.tsx`.
If the name has 3 or more words, it is okay to omit the "`Page`". The second is `FooBarPage.test.tsx`.
This will house the tests for the current page. Finally, we have the `page.tsx` file. This will contain
the following code:
```typescript
import FooBarPage from "./FooBarPage";
export default FooBarPage;
```
Exporting page component:
To export a page, we use the following as opposed to named exports.
```typescript
export default function FooBarPage()
```
#### UI
For our frontend components, we try to stick to shadcn for custom components (Dialogs, etc),
lucide for our icons, framer-motion for animations, and react-hook-form for input forms
(sometimes we have non react hook form inputs which is fine, but this library gives some nice features
for validation, etc.)

#### Testing
For testing, we will be using the live backend to test interactions on the frontend, so our frontend
will essentially house integration tests. We are using Jest for testing, and the following setup should be
applied:

```typescript
import {login, logout} from "@/features/user/userSlice";

describe('FooBarPage Component', () => {

    beforeEach(async () => {
        injectStore(store);

        await store.dispatch(
            //@ts-ignore
            login({email: 'testuser@example.com', password: 'password123'})
        );
    });

    afterEach(async () => {
        jest.clearAllMocks();
        await store.dispatch(
            //@ts-ignore
            logout()
        );
    });

    it('knows true is true', () => {
        expect(true);
    });
});
```

This will allow the user to be logged in for any tests that need to occur (if needed, these can be
omitted in cases where you want to test functionality when the user isn't logged in). However, `describe`
sets up the test suite for the page, and we have some actions that happen before and after each test.
Finally, we can write tests with `it('does this thing') () => { /* test logic */ });`.

### `/components`
The components houses react components used for different pages. We have a `\custom` folder with
our custom components, and a `\ui` folder for shadcn components. 

#### '/custom'
We don't have substructure for custom components at the moment, but if this gets too cluttered,
you can always put single use  components in a components folder adjacent to a page (in `\app`).
However, in its current state, it is fine to put components you make in here, just in case
we want to reuse them for other pages.

#### '/ui'
These are custom shadcn components. Feel free to edit them if it feels necessary. These components
are generated by calling `npx shadcn add component-name`. Check out the shadcn page
[here](https://ui.shadcn.com/docs/components) to find new components and see what they look
like. You can also find further shadcn documentation here as well.

### `/features`
This is the core of how we integrate the frontend with api calls. Here, we have folders that
correspond to different slices. Each slice is in the same format as this:
```typescript
/* @/features/search/searchSlice.ts */
import { createSlice, createAsyncThunk } from "@reduxjs/toolkit";
import axios from "@/api/axiosInstance";
import { ParkingSpace, SearchRequest, SearchResponse } from "@/types/type";

interface SearchState {
  loading: boolean;
  error: string | null;
  spots: ParkingSpace[];
}

const initialState: SearchState = {
  loading: false,
  error: null,
  spots: [],
};

export const searchSpots = createAsyncThunk<
    SearchResponse,
    SearchRequest,
    { rejectValue: string }
>("search/spots", async (searchRequest, { rejectWithValue }) => {
  try {
    const response = await axios.post<SearchResponse>("/search", searchRequest);
    return response.data;
  } catch (error: any) {
    return rejectWithValue(error.response?.data?.message || "Search failed");
  }
});

const searchSlice = createSlice({
  name: "search",
  initialState,
  reducers: {
    errorReset(state) {
      state.error = null;
    },
  },
  extraReducers: (builder) => {
    builder
        .addCase(searchSpots.pending, (state: SearchState) => {
          state.loading = true;
          state.error = null;
        })
        .addCase(searchSpots.fulfilled, (state: SearchState, action: any) => {
          state.loading = false;
          state.spots = action.payload;
        })
        .addCase(searchSpots.rejected, (state: SearchState, action) => {
          state.loading = false;
          state.error = action.payload as string;
        })
        .addMatcher(
            (action: { type: string }): action is { type: "search/resetSpots" } =>
                action.type === "search/resetSpots",
            (state : SearchState) => {
              console.log("Resetting spots");
            }
        );
  },
});

export const { errorReset } = searchSlice.actions;
export default searchSlice.reducer;
```
The main parts of this are the state, the async thunks, and the reducer.

#### State
State is the definition of what this slice will hold. For SearchState we mainly have
an array of spots (`ParkingSpace` objects). This is because when we search, the only data
we need to display to the user based on their query is the parking spaces that match.
So, we are able to have a place to put these spaces. The state is essentially what the
frontend components.
```typescript
interface SearchState {
  loading: boolean;
  error: string | null;
  spots: ParkingSpace[];
}

const initialState: SearchState = {
  loading: false,
  error: null,
  spots: [],
};
```
We can access this state in a page with the AppSelector, and this is how it is
done for the search page:

```typescript
// ...
import {useAppSelector} from "@/store/hooks";
// ...
const parkingSpots = useAppSelector((state) => state.search.spots);
// ...
```
The `search` part of the useAppSelector call comes from the
fact that the searchSlice maps to the search field in `/store/index.ts`:
```typescript
// ...
import searchReducer from '@/features/search/searchSlice'
// ...
search: searchReducer
// ...
```

#### Async Thunks
Async thunks are essentially functions that can call apis and let the reducer know
asynchronously if the response is rejected, pending, or successful. Here is the
thunk for the post in the search slice:
```typescript
export const searchSpots = createAsyncThunk<
    SearchResponse,
    SearchRequest,
    { rejectValue: string }
>("search/spots", async (searchRequest, { rejectWithValue }) => {
  try {
    const response = await axios.post<SearchResponse>("/search", searchRequest);
    return response.data;
  } catch (error: any) {
    return rejectWithValue(error.response?.data?.message || "Search failed");
  }
});
```
This request takes a search request object, returns a search response object, and
posts the `/search` endpoint with the `searchRequest` that is passed in. If it recieves
a successful response code, it will return the data in the form of a `SearchResponse`,
otherwise, it will update the thunk's state as rejected and give the string
`"Search Failed"` (unless the error has a message). You can have as many thunks as you
want in a slice as long as you beleive they should be editing/corresponding to the same
data in the state.

To call a thunk in a component you do the following:
```typescript
// ...
import { useAppDispatch } from '@/store/hooks';
// ...
export default function SearchPage() {
    const dispatch = useAppDispatch();
// ...
    const onSearch = async () => {
        // ...
        try {
            await dispatch(searchSpots(request));
            setIsSearchOpen(false);
        } catch (error) {
            console.error('Search failed:', error);
        }
    }
// ...
}
```
Given that the spots are gotten using the app selector, they will automatically update
whenever the reducer changes them. Now, lets get to the reducer.

#### Reducer
The reducer is what allows the api calls to change state depending on if they are
loading, rejected, or successful. Here is the example from the search slice:
```typescript
const searchSlice = createSlice({
  name: "search",
  initialState,
  reducers: {
    errorReset(state) {
      state.error = null;
    },
  },
  extraReducers: (builder) => {
    builder
        .addCase(searchSpots.pending, (state: SearchState) => {
          state.loading = true;
          state.error = null;
        })
        .addCase(searchSpots.fulfilled, (state: SearchState, action: any) => {
          state.loading = false;
          state.spots = action.payload;
        })
        .addCase(searchSpots.rejected, (state: SearchState, action) => {
          state.loading = false;
          state.error = action.payload as string;
        })
        .addMatcher(
            (action: { type: string }): action is { type: "search/resetSpots" } =>
                action.type === "search/resetSpots",
            (state : SearchState) => {
              console.log("Resetting spots");
            }
        );
  },
});

export const { errorReset } = searchSlice.actions;
export default searchSlice.reducer;
```
This builds the slice and adds cases to how we should reduce certain actions. For example,
if the searchSpots post gets a 200 back, then the associated thunk is said to be
fulfilled (successful). From there, our reducer does the following:
```typescript
addCase(searchSpots.fulfilled, (state: SearchState, action: any) => {
          state.loading = false;
          state.spots = action.payload;
})
```
Here we take the payload from our post and assign this return value (an array of
ParkingSpace objects) to our state of spots. This will mean any component that is
using the app selector and tied to these spots will update the stored spots to the new
value of the post. This means that if a frontend component maps this array to
subcomponents/html, it will render the new array which will allow the visual state to update.

Feel free to add more slices as we call more api endpoints. Ideally, these should align with the
names of our endpoints, but in cases of overlap, it is possible to call other endpoints
in thunks as well. You should only ever need one thunk for an endpoint, unless it is
very generalized and needs to update multiple types of data on multiple pages.

### `/hooks`
Custom React hooks for managing application state and side effects.

### `/lib`
Shared library functions, utilities, or helpers for application logic.

### `/mocks`
Mock api endpoints and mock data. We won't be prioritizing mocks as much, but they
are called at base url `https://localhost:3000/v1`. Feel free to look more into MSW
(Mock Service Worker) [here](https://mswjs.io/docs).

### `/pages`
Next.js requires this to be here, we are using the app router, meaning we don't put pages here.

### `/store`
This is where the core Redux store is initialized. If you make a new slice, you must add it
to the `index.ts` file. We also have middleware for logging redux states and populating
with localStorage data in the case of a refresh. Here is how you add a new slice:

```typescript
// ...
import newReducer from '@/features/new/newSlice'
// ...
export const createStore = (preloadedState?: Partial<RootState>) => {
  const store = configureStore({
      reducer: {
          // @ts-ignore
          add: addReducer
          // more reducers...
          // !! add a new reducer here!!
      }
  });
}
```

### `/types`

#### `type.ts`
TypeScript type definitions used for props, API responses, or general type enforcement.
You can add types to the `type.ts` file.

#### `generated.ts`
Types generated from our openapi. If you update the open api, cd into the `/frontend`
directory and run:
```
npx openapi-typescript ../docs/api/openapi.yaml --output ./src/types/generated.ts
```
You can retrieve the types in generated.ts for the app by making a new type in `type.ts`
in the following format:
```typescript
export type NewType = components["schemas"]["NewType"];
```

## Additional Notes

### Use Client
Make sure that for any frontend component (page or custom component) you include:
```typescript
'use client'
```
This should be at the top of the file and it tells next.js that this is a client
component, so it can render it for the client. Other components / .ts files that do
not have this are server components and can make api calls, etc. However, certain things
like the user's router path, etc. are hidden in server components, so ensure that
you find workarounds if you need a server component to use this type of information
(sometimes drilling into a client component within a server component can achieve this)

### Environment Setup
- Configure `.env.local` similar to how it is done in `.template.env`:
```env
NEXT_PUBLIC_API_BASE_URL=http://localhost:5000/api/unstable
NEXT_PUBLIC_BASE_URL=http://localhost:5000
NEXT_PUBLIC_GOOGLE_MAPS_API_KEY=key
```
